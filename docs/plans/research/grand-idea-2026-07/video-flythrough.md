# video-flythrough — research + stress-test (2026-07-03)

**Headline:** Video-gen fly-throughs are commercially viable for concept/pitch clips today, but no model preserves architectural geometry across a camera path without 3D-grounded conditioning — the product-critical path is depth/point-cloud-conditioned video-to-video (GEN3C/DepthDirector-style research, or open Wan2.2-Fun-Control-Camera), not naive text/image-to-video.

## Key facts

- Seedance 2.0 (ByteDance, released Apr 9 2026): up to 15s@720p, native audio, director-level camera control, $0.10-0.30/sec depending on host [fal.ai/seedance-2.0, github.com/fal-ai/seedance-2.0-api]
- Kling 3.0/O3 Omni One (early-mid 2026): Curve Dolly Camera Path editor with 2-8 control points + interpolation curves, up to 6 auto-planned camera cuts, up to 15s clips [kling3.pro/blog/kling-3-0-motion-control-guide]
- Veo 3.1 (Google, latest update Jan 2026) remains Pre-GA and its terms explicitly prohibit commercial use even on paid plans without separate written authorization [licenseorg.com/blog/ai-video-licensing-2026]
- Luma Ray3.2 (released June 9 2026) API supports Multi-Keyframe (16 keyframes/clip) and a Modify Video (V2V) mode accepting manual pose/depth/normals/trajectory conditioning signals -- the most explicit commercial geometry-conditioning feature found [lumalabs.ai/api, lumalabs.ai/news/introducing-ray-3-2]
- Runway Gen-4.5: $0.12/sec, 2-10s@720p, camera control, no native audio, closed/no self-host [docs.dev.runwayml.com/guides/pricing]
- Open-source Wan2.2-Fun-Control-Camera (Alibaba, HF) supports Canny/Depth/Pose control-video conditioning plus dedicated camera-lens-control weights, self-hostable [huggingface.co/alibaba-pai/Wan2.2-Fun-5B-Control-Camera]
- HunyuanVideo-1.5 (Tencent, Nov 2025): 8.3B params, runs on consumer GPUs 12-24GB VRAM, open weights, community camera-motion LoRAs [github.com/Tencent-Hunyuan/HunyuanVideo-1.5]
- Research frontier for geometry-true camera-conditioned video: NVIDIA GEN3C (CVPR 2025, 3D point-cloud cache conditioning), DepthDirector (Jan 2026, depth-video dual-stream conditioning trained on Unreal Engine synthetic data), DualCamCtrl (Nov 2025, >40% camera-motion-error reduction), CtrlVDiff (Tele-AI, code released) -- none are hosted commercial APIs yet
- 256 Grays practitioner post-mortem (May 2026): AI video is 'useless at anything where the building has to look the same in frame 1 and frame 240'; base render for any multi-view/video package is always traditionally rendered, never AI [256grays.com/insights/90-percent-time-saving-myth-with-ai-in-archviz]
- Standard current studio workaround: render 2 keyframes (start+end) traditionally in the 3D engine, let Kling/Veo interpolate motion between them -- fails on complex orbital camera moves [aifire.co/p/ai-vs-render-farm-professional-archviz-workflow-2026]
- Chaos 2026 survey (~800 architects): 48% cite inconsistent/poor AI output quality as top challenge, only ~1/3 more than 'somewhat satisfied' [blog.chaos.com/statistics-ai-architectural-design-and-visualization]
- Commercial licensing: Kling grants Kuaishou broad royalty-free rights over inputs/outputs (China/Singapore jurisdiction); Seedance 2.0 commercial-viable on Pro/API tier but flagged as legally fraught given training-data disputes [licenseorg.com/blog/ai-video-licensing-2026]

## Recommendation

Do not build the video-flythrough feature on plain text/image-to-video prompting -- every current source confirms diffusion video hallucinates/warps building geometry across camera motion, mirroring this project's own known multi-view drift problem. Instead: (1) ship a low-risk MVP first using the "first & last frame" pattern already proven by working studios -- render 2 keyframes from web3d-prototype's own camera path, feed them to Kling 3.0 (Curve Dolly) or Luma Ray3.2 (multi-keyframe) for in-between interpolation; this is buildable today with existing camera/render code at roughly $0.50-3/clip. (2) In parallel, treat depth/G-buffer-conditioned video-to-video (GEN3C/DepthDirector/CtrlVDiff pattern, or the open self-hostable Wan2.2-Fun-Control-Camera on Modal) as the real long-term architecture -- it is the direct video-domain extension of the FLUX+ControlNet-Union approach already shipped for the hero render, and it is where the research frontier is converging. (3) Exclude Google Veo from any commercial/client-facing use until it exits Pre-GA, and flag Kling/Seedance's China-jurisdiction data-licensing terms for the user's later legal review before any client-facing deployment. (4) Any live API test of these models needs explicit user budget authorization -- per-clip costs ($0.50-$4+) are far above the project's $0.05/session cap.

Pricing varies by host: fal.ai $0.24–0.30/sec, Replicate/WaveSpeed $0.10–0.30/sec effective, EvoLink as low as $0.045/sec. Supports video-editing (restyle existing video) and reference-to-video. Also supports Start/End-Frame-to-Video and per-subject Motion Control. REST API takes camera keyframes as JSON. [kling.ai/quickstart/klingai-video-3-model-user-guide, kling3.pro/blog/kling-3-0-motion-control-guide, ai-motioncontrol.com/kling3]
- **Google Veo 3.1** (`veo-3.1-generate-preview`, latest update Jan 2026): 8s native clips, 720p/1080p/4K w/ upscaling, native audio, first/last-frame transition generation, up to 3 reference images for character/style consistency, scene-extension chaining for >1min sequences. **Critical: Veo remains Pre-GA — Google's terms explicitly prohibit commercial use even on paid plans** without separate written authorization [licenseorg.com/blog/ai-video-licensing-2026; ai.google.dev/gemini-api/docs/models/veo-3.1-generate-preview].

- **Luma Ray3.2** (released June 9 2026) — the most product-relevant find: full API exposing **Multi-Keyframe control (up to 16 keyframes per clip)**, plus a distinct **video-to-video "Modify Video" mode that accepts manual signal conditioning: pose, depth, normals, trajectory, face** — i.e., explicit frame-conditioned/geometry-guided generation is a first-class, documented API feature, not a research paper. Pricing: T2V/I2V $0.15–1.20 per 5s (540p–1080p); V2V $0.72–4.32 per 5s; HDR/EXR output for pro pipelines; no-train guarantee available on Provisioned Throughput tier. [lumalabs.ai/api, lumalabs.ai/news/introducing-ray-3-2, docs.agents.lumalabs.ai/guides/pricing]

**Open-source / self-hostable options:**

**The core product question — frame-conditioned/depth-conditioned video-to-video for geometry-true fly-throughs — is an active, hot research area, not yet commercially productized end-to-end:**
- **NVIDIA GEN3C** (CVPR 2025): generates video conditioned on a 3D point-cloud "cache" (from depth of seed images) reprojected under a user-specified camera trajectory — architecturally exactly what a real-time 3D engine could feed it (render depth from your camera path → condition GEN3C). Code/research release, not a hosted API. [research.nvidia.com/labs/toronto-ai/GEN3C, arxiv.org/pdf/2503.03751]
- **DepthDirector** (Jan 2026, arXiv 2601.10214): "View-Content Dual-Stream Condition" — injects both source video AND warped depth sequence (rendered under target viewpoint) into a pretrained video diffusion model via LoRA adapter; trained on an 8K-video Unreal-Engine-rendered multi-camera dataset (MultiCam-WarpData) — i.e., synthetic 3D-engine-rendered training data, same idea as this project's own reproject-from-3D approach.
- **DualCamCtrl** (Nov 2025, arXiv 2511.23127): dual-branch RGB+depth diffusion, reports >40% reduction in camera-motion error vs. prior geometry-conditioned methods.
- **CtrlVDiff** (Tele-AI, Nov 2025): unified model conditioning on depth+normals+segmentation+edges+albedo/roughness/metallic simultaneously — closest to "render our G-buffer, get back a photoreal video," code released on GitHub (Tele-AI/CtrlVDiff).
- **Vid-CamEdit** (AAAI 2026) and **LaVR** (arXiv 2601.14674): both reformulate camera-trajectory video editing as geometry-grounded video-to-video, both report SOTA vs. naive/no-geometry baselines on extreme-trajectory extrapolation — the exact "back side of the building" failure mode already hit in this project's own full-360 reproject work.
- **None of these research systems are hosted commercial APIs today.** The nearest productized approximation is Luma Ray3.2's V2V mode (depth/normals/trajectory as manual signals) and Wan2.2-Fun-Control-Camera (open, self-hostable, Canny/Depth conditioning + camera-lens presets).

**Direct product implications for this project:**
1. Do not build the fly-through feature on naive T2V/I2V prompting from a single screenshot — every source (studios, model vendors' own docs, and the geometry-preservation literature) converges on the same failure: unconstrained diffusion video cannot hold a building's geometry across a moving camera, especially past ~90° of unseen rotation. This directly corroborates the project's own multi-view-drift finding from the hero-render spike.
2. The only technically sound path that matches your existing architecture (real-time 3D engine with per-pixel depth/ID buffers already computed) is **depth/G-buffer-conditioned video-to-video**, i.e., render N frames of camera-path RGB+depth from web3d-prototype, then condition a video diffusion model on that depth/canny sequence rather than letting it hallucinate structure from a single image. This is exactly the GEN3C / DepthDirector / CtrlVDiff / Wan2.2-Fun-Control-Camera pattern — and it is a direct video-domain extension of the FLUX+ControlNet-Union approach already shipped for the hero render.
3. Nearest working building block today: **Wan2.2-Fun-14B-Control-Camera** (open, self-hostable on Modal, Canny+Depth conditioning) or **Luma Ray3.2's V2V "Modify Video"** mode (hosted, accepts depth/normals/trajectory signals, $0.72–4.32 per 5s at 540–1080p) — both let you supply a geometry-locked control signal rather than trusting the model's own inference.
4. The proven, cheap, low-risk interim workflow used by working studios — **render 2 keyframes from your 3D engine (start/end of a shot), let a commercial model (Kling 3.0 Curve Dolly, or Luma Ray3.2 multi-keyframe) interpolate the in-between motion** — is directly buildable today with existing web3d-prototype camera/render code, at ~$0.50–2 per clip, and matches what "The 2026 archviz pulse" describes as the mainstream studio pattern. This is a much lower-risk MVP than full depth-conditioned V2V and should be the first fly-through experiment.
5. Avoid Veo for any client-facing/commercial deliverable until it exits Pre-GA; avoid Seedance/Kling for legally sensitive client work given China-jurisdiction data-licensing terms, unless the fly-through is purely internal concept exploration.
6. Cost caution: even the cheapest viable per-clip prices ($0.50–$3 for a 5–10s clip) are 10–100x this project's stated $0.05/session budget — any live test of these APIs requires explicit user authorization to raise the cap, exactly as the CLAUDE.md hard rules require.

## Adversarial stress-test (Opus 4.8)

**Verdict:** viable-with-changes

**Fatal flaws:**

- none

**Risks:**

- INCUMBENT-RESPONSE (most severe, report ignores it entirely): The report's flagship recommendation — render 2 keyframes from the 3D engine, let a hosted model interpolate — is ALREADY a shipped commodity feature in direct competitors. Carve (carve.so/features/animate) does exactly this today: Veo 3.1, 20+ camera-motion presets, bookend first/last-frame interpolation, operates on existing renders, 'client-ready MP4 in under 90 seconds,' plus AI rendering + material swap + 4K upscale in one product. Vibe3D (vibe3d.ai) markets 'SketchUp/Revit/3ds Max -> cinematic walkthroughs.' The report presents the keyframe-interpolation MVP as a differentiated 'low-risk first experiment,' but it is table stakes an integrated ArchViz-AI startup already offers. Building it buys near-zero moat. The report did zero competitive scan on shipped products offering this feature — a serious omission for a viability judgment.
- COMPOUNDING ERROR across the pipeline the grand idea actually proposes: The flythrough dimension is not standalone — the grand vision chains image-gen entourage -> video-gen flythrough -> world-model splat reconstruction. Every stage that touches this dimension inherits geometry drift. The report validates ONLY the isolated 2-keyframe interpolation case and explicitly concedes it 'fails on complex spiral/orbital moves and dimension-critical close-ups' (AIFire, Hailuo 'melting/shearing' of mullions). Architecture flythroughs are precisely orbital reveals and facade-grid close-ups. So the one case that works is the case architects least want, and the cases they want most are the documented failure modes. The report's own sources (256 Grays, Spline Dynamics) say the base render is ALWAYS traditional and 'AI never carries the geometric load' — meaning this dimension can only ever be a garnish on a traditional pipeline, not a load-bearing product pillar.
- REVISION-CYCLE breakage (the prompt's explicit stress test): 'Move the window 2 ft' arriving after renders are done. In a traditional 3D pipeline this propagates deterministically to all frames. In every AI-video path here it does not. Keyframe interpolation requires re-rendering BOTH endpoints traditionally and regenerating (paying again, ~$0.5-3), and the interpolated middle may not match the prior approved take (stochastic, seed-fragile). Depth-conditioned V2V re-runs the whole clip and drifts. Spline Dynamics states plainly: 'a revision means regenerating the image, and elements already approved may not survive intact... a fundamental limitation' for multi-round client work. Non-destructive editing is a CORE stated product value — and AI video is structurally destructive under revision. This is survivable only if the feature is scoped to early concept/pitch clips where revisions are cheap, never to deliverables.
- GEOMETRY-CONDITIONING claim is overstated for the one hosted product cited as the mitigation. Luma Ray3.2's 'Modify Video' per-signal controls (depthBlur, normalsAugmentation, trajectorySparsity) are documented as knobs that LOOSEN geometry to grant 'more reinterpretation' (runware.ai/docs, lumalabs Modify docs) — they are creative-restyle dials, not a hard geometry LOCK the way FLUX+ControlNet-Union depth conditioning is for the shipped hero render. The report frames Ray3.2 V2V as 'the most explicit commercial geometry-conditioning feature found' and 'geometry-guided generation as a first-class API feature.' That reads the feature backwards: it's built to preserve MOTION/performance while restyling appearance, not to preserve building geometry across a camera path. Verify before relying on it as the productized mitigation.
- COST/LATENCY at product usage, understated. Self-hosted Wan2.2-Fun-A14B-Control benchmarks at ~520s for ONE 5s clip at 640x640 on a 24GB 4090 (comfyui-wiki verified); 4-step LoRA cuts to ~79-138s but at quality cost. On Modal scale-to-zero the 64GB weight load adds a multi-minute cold start per invocation, and product-grade resolution (1024+, 15s) multiplies GPU-seconds. A real flythrough deliverable is many takes x many shots x many revisions — the hosted per-clip prices ($0.5-4.3/5s Luma, $0.24-0.30/s Seedance) compound into $10s-100s per client sequence, 200-8600x the $0.05 session cap. Financially the self-host-vs-API math the project usually wins on is far weaker here than for the ~$0.01-0.02 hero still render.
- LICENSING/JURISDICTION concentration risk (report flags but under-weights the squeeze): Veo is Pre-GA, commercial-prohibited — yet it is the ONLY model a shipped competitor (Carve) uses for this feature, and the report's own recommended fallbacks (Kling, Seedance) carry China/Singapore jurisdiction + broad Kuaishou input/output licensing + 'too legally fraught to recommend' (LicenseOrg). That leaves Runway Gen-4.5 (US, commercial, but closed/no self-host, no indemnification outside Enterprise) or self-host Wan (Alibaba license, unresolved training-data provenance) as the only clean client-facing options. For a tool sold to architecture firms who carry professional liability, 'which model can we legally ship a client deliverable on' has a genuinely thin answer today.

**Recommendations:**

- Reposition this dimension from a product PILLAR to a concept/pitch GARNISH. The evidence (256 Grays, Spline Dynamics, Zenviz, Chaos survey) is unanimous: AI video is viable ONLY for early-stage concept/investor/competition clips where geometry precision and revision-stability don't matter, and traditional rendering always carries client-deliverable and legally-sensitive work. Scope the feature to that lane explicitly, or it will fail on contact with a real firm's deadline+revision cycle.
- Do a shipped-competitor teardown BEFORE building anything. Carve and Vibe3D already ship the recommended keyframe-interpolation MVP. Answer 'what do we do that Carve doesn't' first. The one defensible answer this project has: it owns the live 3D engine (web3d-prototype) with per-pixel depth/ID buffers and the FLUX+ControlNet-Union hero pipeline — so its differentiation is NOT the video model but the geometry-locked control signal fed to it, and the round-trip back into an editable 3D scene. Build only the differentiated slice; do not rebuild the commodity interpolation feature as if it were novel.
- If pursued, invest in the depth/G-buffer-conditioned V2V path (Wan2.2-Fun-Control on Modal, or CtrlVDiff pattern) as the ACTUAL product, and treat keyframe-interpolation only as a throwaway probe — but budget honestly for it: it is a research-grade integration (self-host, cold starts, quality tuning at real resolution), not a weekend spike. Do NOT rely on Luma Ray3.2 V2V as the geometry-lock mitigation without first testing whether its depth/normals controls preserve building geometry rather than loosen it — the docs suggest the latter.
- For any client-facing deployment, resolve licensing first: default to Runway Gen-4.5 (US/commercial) or self-hosted Wan for deliverables; confine Kling/Seedance/Veo strictly to internal concept exploration. This is a gating legal question for a liability-bearing customer, not a later cleanup item.
- Gate every live API test behind explicit budget authorization — per-clip $0.5-$4 is 10-100x the session cap, and a realistic multi-take/multi-shot evaluation run is $10s-100s. Set a hard experiment budget with the user before any --live flythrough call.
