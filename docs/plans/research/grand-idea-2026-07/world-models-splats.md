# world-models-splats — research + stress-test (2026-07-03)

**Headline:** World models + Gaussian splats can produce editable 3D environments today at "impressive demo" quality, but true architect-grade precise editing (place/remove a specific labeled asset, relight correctly, no artifacts) is still a research-to-early-product transition — the pragmatic 2026 move is compositing real meshes (your existing pipeline) into a Marble/HunyuanWorld-generated splat backdrop via Spark, not editing the backdrop's own splats directly.

## Key facts

- World Labs Marble is out of beta in 2026, API at docs.worldlabs.ai/api; credits $1.00/1,250, world generation = 1,500 credits (~$1.20) for marble-1.1 (source: docs.worldlabs.ai/api/pricing)
- Marble exports: SPZ/PLY splats (2M or 500k Gaussians), collider mesh GLB (100-200k tri), high-quality mesh GLB (600k-1M tri, up to 1hr generation, rate-limited 4/hr) — docs.worldlabs.ai/marble/export/specs
- Marble editing tools are Pano Edit (2D panorama diffusion edit → world regeneration), Chisel (block-out geometry), and Compose/Studio (stitch multiple worlds + camera paths) — not direct per-Gaussian object editing
- Spark (@sparkjsdev/spark), already used in this project, is built by World Labs itself; its own GitHub issue #49 confirms splat-native shadows are unsolved and the recommended workaround is a proxy mesh shadow-catcher — i.e., what this project already does
- Google Genie 3 / Project Genie added Street View grounding in May 2026, letting generated worlds anchor to real-world locations via Maps Imagery (source: blog.google, May 19 2026)
- Decart Oasis 3 ($0.02/sec API, <200ms latency) and Odyssey-2 Max are real-time world models but purpose-built for autonomous-vehicle/robotics simulation, not asset-editable creative environments
- Tencent HY-World 2.0 (open-source, Apr-May 2026) provides WorldMirror-2 (recon), HY-Pano-2 (pano gen), WorldStereo-2 (pano-to-3DGS) with public HuggingFace weights — a self-hostable alternative to Marble
- Object insertion with correct relighting/shadows into existing Gaussian splats remains active 2026 research (LightHarmony3D, ComGS, GHPT) with explicitly acknowledged limitations for complex scenes — not a solved, production-ready capability
- SuperSplat (PlayCanvas, open-source, MIT) is the most mature browser-based splat editor, but its selection tools are geometric/color-based, not semantic object-aware editing
- Nerfstudio 1.4 + gsplat (splatfacto/-W/-MCMC) is the de facto open pipeline for video/photo-to-3DGS reconstruction; known to underfit on very large scenes (>2000 sq ft) or >3k images (GitHub issue #3743)
- Polycam (LiDAR, 1-2cm accuracy, auto floor plans, $150-400/yr) is the better-fit consumer capture app for architects documenting real sites vs Luma AI (best visual quality, no dimensional accuracy)

## Recommendation

Do not attempt to make the splat backdrop itself precisely editable in the near term — that's still a research problem across every lab publishing in 2026. Instead, extend the existing mesh+Spark compositing approach: use Marble (or self-hosted HY-World 2.0 to cut cost) purely to generate/capture an immersive, non-editable environment backdrop, and keep all architect-facing editing (materials, entourage placement, massing) in the mesh layer where the click-to-edit tooling already works. If a "remove that one tree from the backdrop" feature is wanted, prototype narrowly with SAM-HQ-based segmentation + Gaussian Grouping-style masking rather than building a general insertion/relighting editor — that's the one editing primitive close enough to product quality to ship in 2026. Track Genie 3's Street View grounding as a way to ground backdrops in the real site context, and watch HY-World 2.0 as a cost lever against Marble's per-generation credit pricing.

## Full report

## World-generation models (mid-2026 state)

**World Labs Marble** is the clear product leader (Fei-Fei Li's company; Spark — which you already use — is built by World Labs). Went out of open beta in 2026. Inputs: text, single image, multi-image (with azimuth positions), video, or 360° panorama. Models: `marble-1.1` (1,500 credits/gen, ~$1.20), `marble-1.1-plus` (1,500–3,000 credits, expands coverage for large worlds), `marble-1.0-draft` (150 credits, fast iteration). Credits: $1.00/1,250, $5 minimum purchase. API separate billing from the web-app (docs.worldlabs.ai/api/pricing, docs.worldlabs.ai/api/models). Note the API's World Generation endpoint bills TWO events per call typically (pano-gen + world-gen).

**Editing tools in Marble (the crux of your question):**
- **Pano Edit** — edit the underlying 360° equirectangular panorama with a text prompt + selection mask ("select edit area," describe change, "add snow-covered trees," etc.), then regenerate the 3D world from the edited pano. This is diffusion-level 2D editing lifted back to 3D, not direct Gaussian manipulation — every edit is effectively a re-generation pass (docs.worldlabs.ai/marble/edit/pano-edit).
- **Chisel** — block out coarse 3D geometry (architectural massing) as a scaffold Marble generates detail onto (docs.worldlabs.ai/marble/create/chisel-tools).
- **Compose/Studio** — stitch multiple separately-generated worlds into one larger continuous environment, plus camera-path/flythrough authoring (docs.worldlabs.ai/marble/create/studio-tools/compose). A game-dev case study (José Tijerín, "Gaussian Mansion") used exactly this: multiple Marble worlds exported as `.ply`, stitched in Marble Studio, then imported to Unreal — real production use, but for game/film backdrops, not precision architectural editing.
- **Export**: SPZ (World Labs' native, ~2M or 500k splats) and PLY (broader compat, same counts), plus a **collider mesh GLB** (100-200k tris, physics-only) and an optional **high-quality mesh GLB** (600k-1M tris with textures/vertex color, up to 1hr to generate, rate-limited 4/hr/user). Coordinate system is OpenCV (+x left, +y down, +z forward) — needs a Y/Z flip for OpenGL/three.js, which your pipeline already handles via similar conventions presumably.

**Competing world models**: Google DeepMind **Genie 3 / Project Genie** — text/image → real-time explorable environment; now (May 2026) added **Street View grounding** so worlds can anchor to real places via Maps Imagery — directly relevant if you ever want a real-site-grounded splat context rather than pure generation. Gradual rollout to Google AI Ultra ($200/mo) subscribers. Decart **Oasis 3** ($0.02/sec API) — extremely photorealistic but purpose-built for autonomous-vehicle/robotics simulation (multi-camera, action-conditioned), not asset-editable scenes — not a fit. Odyssey (Starchild-1, Odyssey-2 Max) — also robotics/agent-training focused. **Tencent HY-World 2.0** (open-source, Apr–May 2026) is the notable open alternative: WorldMirror-2 (multi-view/video→3D, ~1.2B params), HY-Pano-2 (text/image→360° pano, ~80B), WorldStereo-2 (pano→3DGS, ~17B) — all weights on HuggingFace. This is the one to prototype with if you want to self-host rather than pay World Labs API credits.

## Video/photo → 3DGS reconstruction (the "real environment capture" path)

**Nerfstudio 1.4 + gsplat** remains the open-source standard: `splatfacto` (baseline), `splatfacto-W` (masks moving people/backgrounds — good for real-site capture), `splatfacto-MCMC` (auto-adjusts Gaussian count). ~12 min on RTX 4090 for a small scene. Known issue: splat counts collapse on very large scenes (>2000 sq ft) or >3k images (github.com/nerfstudio-project/nerfstudio/issues/3743) — relevant if you'd reconstruct a full building site. **Postshot 2.0** (Jawset) is the Windows GUI alternative, bakes 6M Gaussians on 12GB VRAM, `.ksplat` export. **Luma AI** (best visual quality, cloud, free tier, <1 min processing, Genie 2 for text/video→mesh+splat, "Interactive Scenes" free-orbit) and **Polycam** (LiDAR on iPhone 12 Pro+, 1-2cm accuracy, floor plans, $150-400/yr Pro/Business) are the consumer capture apps — Polycam is the better fit for architects documenting real sites (floor-plan auto-generation, professional export formats GLTF/FBX/PLY/USDZ/OBJ).

## Editing splats: segmentation, removal, insertion, relighting (the honest assessment)

**Segmentation**: Gaussian Grouping (2023, foundational — SAM-supervised per-Gaussian identity encoding) still underpins most later work. 2026 advances: SAM-HQ-based prior-guided label reassignment (arxiv 2605.16065) for cleaner boundaries; ArtisanGS (arxiv 2602.10173, Feb 2026, NVIDIA-adjacent authors) — interactive AI+human-in-the-loop 2D-mask-to-3D-selection propagation, explicitly built because "controllable editing techniques for this representation are limited." A June 2026 survey (pubmed 42313584) confirms segmentation/editing/generation as the three active fronts.

**Object removal**: solved reasonably well for isolated objects (Gaussian Grouping's local editing scheme; GScream/ECCV 2024 geometry-and-feature-consistent inpainting) — hole-filling via cross-attention feature propagation from visible regions.

**Object insertion with correct lighting/shadows**: this is the genuinely hard, still-research part, and it's exactly your product's core ask ("place/remove assets, art-direct the scene"). Multiple 2026 papers attack it but all report real limitations:
- LightHarmony3D (arxiv 2603.29209) — hybrid Gaussian-mesh, diffusion-estimated HDR panorama for illumination, PBR shadow compositing.
- ComGS (arxiv 2510.07729) — Surface Octahedral Probes cache occlusion/indirect light for near-real-time relightable insertion.
- A 2025 Fraunhofer thesis (publica.fraunhofer.de/487287) explicitly concludes: "visually coherent... for small-scale object insertions, while revealing fundamental limitations... in more complex insertion scenarios."
- Generative insertion via multi-view diffusion (MVInpainter, ScienceDirect 2025) and GaussianEditor (CVPR 2024, ~5 min per object incorporation) — single-view-inpaint → image-to-3D → concatenate Gaussians. Works for demos; multi-view consistency and scale/depth alignment remain manual/heuristic.

**Relighting**: still an active research decomposition problem, not solved. 2026 papers (SSD-GS, MaterialClusterGS, LumiMotion/CVPR2026, "Intrinsic decomposition and editing of 3DGS" arxiv 2606.31637, GHPT hybrid path tracing/CVPR2026) all show progress on diffuse/specular/shadow/subsurface decomposition but each has caveats (single isolated objects, environment-map-only lighting, no relighting support in some, compute-heavy path tracing). No production tool ships full physically-correct splat relighting yet.

**Splat editors (product-ready today)**: **SuperSplat** (PlayCanvas, open-source, MIT, browser-based) is the most mature — 8 selection tools (rect/polygon/brush/flood-fill/eyedropper/sphere/box), transform gizmos, multi-file merge, histogram-based data-panel selection, Walk Mode (voxel-collision first-person), streamed LOD via the new SOG format, Easy Upload. This is cleanup/composition/curation tooling — not semantic "click this wall" editing; selection is geometric/color-based, not object-aware out of the box (though it can consume Gaussian-Grouping-style labels if you add them).

## Splat + mesh hybrid compositing (directly relevant — you already do this)

**Spark (@sparkjsdev/spark)**, which you're already using, is built by World Labs itself, integrates natively with three.js's rendering pipeline to fuse splat and mesh objects with correct sorting, supports PLY/SPZ/SPLAT/KSPLAT/SOG. Its GitHub issue #49 ("Light & Shadows") confirms the honest limitation: true splat-native shadows aren't solved — the *recommended workaround today* is exactly what you already do (a proxy three.js Mesh/shadow-catcher casting/receiving shadows around the real geometry). Research-level unified rasterization (UniMGS, arxiv 2601.19233 — single-pass mesh+3DGS with anti-aliased blending) exists but isn't shipped in any consumer tool yet.

## Product implication for your architecture

Given all this: **an architect placing/removing arbitrary labeled assets inside a fully-editable splat environment, with correct relighting and shadows, is not achievable at product quality in 2026** — it's an active multi-lab research problem (2026 CVPR/arxiv papers still calling out fundamental limitations). What **is** achievable and already validated in production (game/film case studies): generate or capture a splat **environment backdrop** (Marble/HunyuanWorld/Nerfstudio) and composite your **real, precisely-controlled mesh** (the actual building + entourage you already generate) into it using Spark, exactly as you're doing — this sidesteps splat-editing entirely by keeping the thing the architect actually needs to edit (the building, materials, entourage placement) in mesh-land where your existing click-to-edit tooling already works, and using the splat only for the immersive, non-editable surrounding context (streetscape, landscape, sky). Marble's Compose/Studio world-stitching is a good option for building bigger contextual environments without touching splat internals. World Labs' own architecture case study (worldlabs.ai/case-studies/2-architecture-design) validates this exact use pattern: walkable client presentations, not asset-level editing.

## Notable gaps / what to watch
- Genie 3's new Street View grounding (May 2026) is worth testing — could ground splat backdrops in the actual real-world site context around a project, which none of your current tools do.
- HY-World 2.0 is fully open-source (HuggingFace weights) — worth a cheap local prototype vs. paying World Labs API credits, if self-hosted GPU cost beats $1.20+/generation.
- Object-level segmentation-for-editing (ArtisanGS, SAM-HQ label reassignment) is close enough to product quality that a narrow "select and delete this tree from the backdrop splat" feature is plausible sooner than full insertion/relighting.

## Adversarial stress-test (Opus 4.8)

**Verdict:** viable-with-changes

**Fatal flaws:**

- none

**Risks:**

- DIMENSIONAL FALSITY IS A LEGAL/PROFESSIONAL LANDMINE, NOT JUST an aesthetic one. Third-party benchmarking (thefuture3d.com, Apr 2026) puts GS mean geometric error at 7.82cm +/- 11.49cm vs LiDAR ground truth -- '3-10x worse than photogrammetry, 40-4000x worse than LiDAR,' and explicitly 'the least geometrically accurate method still useful for professional apps.' G3Splat (arxiv 2512.17547) confirms generative/feed-forward splats produce 'geometrically degenerate Gaussians' whose scales/orientations drift because training minimizes photometric not geometric loss. For a Marble/HunyuanWorld-GENERATED backdrop (not even a capture), the surrounding streetscape is hallucinated -- setbacks, street widths, tree heights, adjacent-building massing are invented. If an architect presents this to a client or planning board and the context is materially wrong (a real neighbor's building shown at wrong height, a right-of-way at wrong width), that is a liability exposure the incumbents (Enscape/Lumion) never carry because they composite surveyed context. Mitigation exists (label backdrops 'illustrative context, not survey'; Genie 3 Street View grounding; GCP-constrained capture for real sites) but it must be a hard product rule, not a footnote.
- THE SPLAT BACKDROP IS FROZEN AT ONE MOMENT -- and architects revise constantly. Two independent 2026 industry writeups (aukimi, CG Lounge) confirm the architectural constraint: 'lighting baked into the splat at capture time does not respond to dynamic engine lights... your splat scene looks great at the time of day you captured -- and ONLY at that time of day' and 'you cannot add a key light, remove a shadow, change time of day, or match to a plate.' The project's own mesh layer is suncalc-driven with 4 HDRIs and can re-time freely; the splat backdrop CANNOT follow it. So the moment a client says 'show me this at dusk instead of noon,' the mesh relights and the backdrop doesn't -- a visible lighting mismatch at the exact seam the whole compositing approach depends on. This is survivable (regenerate the backdrop per time-of-day, or restrict splat use to fixed-lighting hero shots) but it caps the splat backdrop to a small number of pre-baked lighting states, which collides directly with the revision-heavy reality of firm workflows.
- 'MOVE THE WINDOW 2 FT AFTER RENDERS ARE DONE' mostly does NOT hit the splat dimension -- it hits the diffusion hero-render dimension, which is the project's already-known weak point. The splat/mesh split is actually the RIGHT answer here: the building stays mesh, so moving the window is a mesh edit and the splat backdrop is untouched. BUT the photoreal HERO output over that composite is a per-view FLUX render, and the project's own state says multi-view consistency of those renders drifts and full-360 is unsolved. So the late-change workflow survives at the geometry/backdrop level but the client-facing photoreal deliverable still has to be re-rolled per view with drift risk. The splat recommendation doesn't cause this, but it doesn't rescue it either -- the risk lives one layer up and the researcher's report is silent on how the frozen splat backdrop stays consistent across the re-rolled hero views.
- LICENSING / CLIENT-IP EXPOSURE ON THE HOSTED PATH. World Labs ToS (dated 2026-01-21) grants World Labs a 'non-exclusive, royalty-free, worldwide license to use, reproduce, modify, adapt' free-account content; commercial rights require Pro+ (Skywork, Marble billing docs) -- so any client-facing deliverable forces the paid tier, and Skywork explicitly warns 'review the privacy policy before uploading client IP; confirm data retention and whether worlds are used for training.' Architects upload confidential, often NDA'd project geometry and site photos. Sending that to a third-party generative API for backdrop generation is a procurement/confidentiality blocker at many firms. This is precisely why the self-hosted HY-World 2.0 lever matters -- but the researcher frames HY-World only as a COST lever, understating that for enterprise/confidential work it may be the only legally viable path, which changes it from 'nice-to-have' to 'required for the design-firm segment.'
- COST/LATENCY AT REAL USAGE IS WORSE THAN THE HEADLINE. Marble billing confirms a world-gen request 'often includes TWO usage events' (pano-gen + world-gen), and 1.1-plus adds 0-1,500 variable credits for larger/outdoor worlds -- so an outdoor architectural context (the actual use case) is 1,600-3,100 credits = ~$1.28-$2.48 per generation, not $1.20, and every time-of-day variant or client revision that changes the backdrop is another full regeneration (there is NO cheap edit -- Pano Edit is diffusion-regenerate at 150 credits/edit + you still re-derive the world). High-quality textured mesh export is rate-limited to 4/hr/user and takes up to 1hr. This is fine for occasional hero shots but does NOT support the iterative, revision-per-hour cadence of a live design charrette -- the economics only work if the splat backdrop is treated as a rarely-changed set piece, reinforcing that it must be scoped as non-editable context, exactly as the researcher concluded.
- INCUMBENT RESPONSE MAY CLOSE THE GAP FASTER HERE THAN ELSEWHERE. Marble's own game/VFX case studies and World Labs' architecture case study validate 'walkable client presentation' -- but that same maturity means Enscape/Twinmotion/D5/Lumion can bolt a splat-backdrop importer onto their existing surveyed-context pipelines with LESS risk than this project, because they already have real georeferenced context and dynamic relighting the splat can be matched against. The differentiator is NOT 'we can show a splat backdrop' (commoditizing fast); it's the direct-manipulation mesh editing + non-destructive material layers the project already owns. The splat dimension should be positioned as a context-enrichment feature, never as the moat.

**Recommendations:**

- ADOPT THE RESEARCHER'S CORE CALL -- it survives adversarial contact. Do NOT build a general editable-splat environment (insertion + relighting + shadows). The 2026 literature I verified (LightHarmony3D arxiv 2603.29209 self-reports dependence on reconstructed-mesh accuracy, breaks on sparse observation / complex indirect light, and adds non-negligible PBR compute cost; D3DR, LumiGauss, and the Fraunhofer thesis all report small-isolated-object-only success) plus two independent industry writeups ('the killer app -- animated, lightable, fully editable splats -- is still in research') confirm this is genuinely unsolved. Keep ALL architect-facing editing in the mesh layer; use the splat only as immersive, non-editable surrounding context via Spark. This is correct.
- MAKE 'ILLUSTRATIVE, NOT SURVEY' A HARD PRODUCT RULE for any generated backdrop. Watermark/label generated context, and NEVER let a measurement/dimension tool read off the splat. Given the 7.82cm mean error and hallucinated generated geometry, a stray 'measure' interaction on a backdrop is a liability event. If a real-site backdrop is needed with any dimensional trust, require capture + GCP constraint (gets ~8cm to ~3-5cm per thefuture3d) or pair with the mesh/LiDAR for the measurable layer -- the splat is the pretty layer, never the true layer.
- PLAN FOR TIME-OF-DAY as pre-baked states, not a live slider, on the backdrop. Because splat lighting is frozen at generation and cannot follow the project's suncalc/HDRI relighting, either (a) restrict splat-backdrop hero shots to the one lighting state they were generated for and disable the sun slider in that mode, or (b) pre-generate a small set (e.g. dawn/noon/dusk) and swap the whole backdrop -- and hide the seam by matching the mesh HDRI to each baked state. Do not promise 'drag the sun and everything relights' when a splat backdrop is present; that check will fail visibly at the mesh/splat seam.
- TREAT HY-WORLD 2.0 SELF-HOST AS A CONFIDENTIALITY REQUIREMENT for the firm segment, not merely a cost lever. World Labs' ToS license grab on free content + Pro-tier-only commercial rights + 'confirm whether worlds are used for training' means client-NDA work likely cannot go through the hosted Marble API. Prototype HY-World 2.0 (WorldMirror-2 / HY-Pano-2 / WorldStereo-2, HF weights) on Modal scale-to-zero specifically to have an on-infra path where no client geometry leaves your control. Fits the existing Modal pattern.
- SCOPE THE ONE SHIPPABLE EDITING PRIMITIVE NARROWLY: 'select and delete an object from the backdrop' via SAM-HQ / Gaussian-Grouping-style masking + GScream-style inpainting. Removal is the one operation the 2026 literature actually calls near-product-quality for isolated objects. Do NOT extend it toward insertion/relighting -- that's where every paper reports fundamental limitations. Ship removal, defer insertion.
- POSITION THE MOAT AS THE MESH-LAYER DIRECT MANIPULATION, not the splat. The splat backdrop commoditizes fast and incumbents can import it too. The defensible differentiator remains the click-a-wall / swap-material / non-destructive-layer tooling the project already owns over real geometry. Ship splats as context enrichment; keep messaging honest that the AI is invisible plumbing and the architect edits real geometry, not a hallucinated cloud.
- ADD A CROSS-DIMENSION CONSISTENCY CHECK the report omits: the frozen splat backdrop must stay stable across the per-view FLUX hero re-rolls that the project uses for photoreal output. Since hero renders already drift per view, verify that compositing a fixed splat behind a drifting foreground render doesn't produce a backdrop-vs-foreground lighting/color mismatch when the client asks for a second camera angle. Test this before relying on splat backdrops for multi-view client decks.
