## What was done

Wrote `spike/end_to_end_edit.py` -- the Spike 4 end-to-end driver that chains the five existing Modal functions plus the T18 local composite helper into a single command. Argument shape matches the task spec exactly: `--screenshot`, `--region-label`, `--material`, plus an opt-in `--live` and a `--dry-run` default.

Pipeline stages each go through `spike.cache.get_or_compute` with a deterministic key derived from sha256 of the relevant inputs. That means a partial failure mid-pipeline (e.g., `apply_material` times out) leaves the earlier stages cached -- the architect can re-run and only pay for the failed-and-after steps. Scopes are split (`render`, `tags`, `mask`, `tile`) so wiping one stage doesn't blow away the others.

`_pick_region(response, label)` returns the highest-confidence region matching the requested label, with deterministic tie-breaking by region id. It raises `ValueError` for an unknown label and `RuntimeError` for "no region with this label in the response" -- silent fallback to a different label would let edits land on the wrong part of the image, which is exactly the failure mode the spike is trying to eliminate.

Dry-run mode prints the full call graph with per-stage cost estimates and a `ESTIMATED COST PER LIVE RUN: ~$0.51 USD` line before any expensive call, matching the task's "cost estimate per live run: ~$0.50 (printed before execution)" requirement.

Live mode imports modal lazily inside `_modal_lookup`, so the dry-run path works without modal CLI auth and the import succeeds in environments without the secrets configured.

## Surprises / notes for the human

- Hit a Windows console encoding issue on first dry-run: I had a U+2192 arrow (`->`) inside `print()` strings, which cp1252 can't encode and crashed the dry-run. Replaced with ASCII `->` everywhere. The module docstring also originally had box-drawing characters; those are gone too. Future scripts in this spike should stick to ASCII for printed output, since Windows defaults to cp1252.
- The Modal `apply_material()` function takes a `material_name: str` (which it formats into an SD-Inpaint prompt) but the task spec says `--material` is "path to a swatch". I bridged the two by taking the file *stem* (e.g., `travertine` from `travertine.jpg`) as the material name. The actual swatch image is not passed to Modal in the spike -- SD-Inpaint isn't material-conditioned. v1 will swap to FLUX Fill + IP-Adapter and at that point the swatch bytes become meaningful; the CLI shape (path, not name) is the right shape for that future call.
- Cache keys are sha256-truncated to 16 hex chars. Collision risk for our use case is nil but if the same screenshot is used with two different prompts the keys diverge correctly because both are hashed in.
- I deliberately did not modify `.gitignore` to ignore `spike/.cache/`. That's still a follow-up from T18.
