## What was done

Created `spike/renderers/flux_bfl.py` with a private `_BflRendererBase`
that encapsulates the BFL submit-then-poll-then-download flow, plus two
public subclasses: `FluxCannyProRenderer` (endpoint
`flux-pro-1.1-canny`, control image field `control_image`) and
`FluxKontextProRenderer` (endpoint `flux-pro-1.1-kontext`, image field
`input_image`). Both read `BFL_API_KEY` from `os.environ` at call time
and raise `RuntimeError("BFL_API_KEY not set")` when missing. The
`requests` import is deferred inside `render()` and helper functions so
that module import requires only the stdlib + `spike.renderers.base`.

Request shape follows BFL's documented JSON contract: POST
`https://api.bfl.ml/v1/<endpoint>` with `{"prompt": ..., "<image_field>":
<base64>, "seed"?: int, "steps"?, ...}` and header `x-key: <api key>`.
Response body is parsed for `id` and `polling_url`; the poller hits
`get_result` every 1.5s for up to 120s and treats `Ready` as success and
`Error|Failed|Content Moderated|Request Moderated` as terminal failure
with a clear `RuntimeError`. On success, the signed `result.sample` URL
is fetched and returned as raw PNG bytes.

## Surprises / notes for the human

- BFL pricing was set at $0.05 per image as a placeholder matching the
  publicly listed FLUX Pro 1.1 rate. Tighten if needed once the official
  pricing page is checked.
- BFL's submit response includes a `polling_url` we honor when present;
  if absent we fall back to `https://api.bfl.ml/v1/get_result?id=<id>`,
  which matches the public docs. T11's `respx` test should exercise both
  branches.
- The Canny variant uses the `control_image` field; Kontext uses
  `input_image`. The field name is the only request-shape difference
  between the two classes — everything else is shared.
- A small set of optional knobs (`steps`, `guidance`, `safety_tolerance`,
  `output_format`, `prompt_upsampling`, `aspect_ratio`) are forwarded via
  `**kwargs` when present so the bake-off driver can sweep them later
  without modifying this file.
