## Verification of each stage

- **Render (cached).** 825 KB matches the original `spike/outputs/spike2/render.png`. Cache key hashing is correct.
- **Tag (cached).** 94 regions match T21 pair 1's count. T23's `parse_tolerant` round-trip preserved the data.
- **Pick.** `_pick_region` chose `wall_1` (the highest-confidence wall at 0.95 across 11 candidates). Bbox in 0–1000 normalized space `(655, 0, 204, 574)` scaled correctly to pixel space `(825, 0, 257, 487)` for the 1259×848 render via `_bbox_norm_to_pixels`.
- **Segment.** SAM2 returned a mask with 8.2% white-pixel coverage of the full 1259×848 frame — that's a sensible wall-only region inside the bbox, not the entire bbox. Saved separately as `spike/outputs/spike4/first_live/mask.png` for inspection.
- **Apply material.** SD Inpaint produced a 512×512 RGB tile (448 KB). The tile shows the entire frame re-imagined (diffusion side-effect — unmasked regions still get latent-reconstructed visually even with the mask supplied), but the *masked region* — the wall — has been resurfaced with what the model interprets as travertine.
- **Composite.** `paste_tile` upscales tile and mask to 1259×848 and runs `Image.composite(tile, base, mask)`: where mask is white the upscaled tile shows through, elsewhere the original render is preserved. Net visible change is confined to the upper-right wall region in the final composite.

## What works

- **End-to-end orchestration:** all 4 Modal functions invoked in the right order, with the right inputs, by `end_to_end_edit.py`. First time the pipeline has ever run on real data; no integration bugs found.
- **Cache pre-population pattern:** the `_short_hash(...)` cache key shape used by `end_to_end_edit.py` is reproducible offline. We can warm the cache for any (screenshot, render) pair we already have on disk and skip the $0.06 of Gemini + Nano Banana calls per run during iterative dev.
- **T23 defensiveness in action:** the tags cache pre-population used `TagRegionsResponse.parse_tolerant`. The driver consumed the cached canonical JSON without complaint. Defensive parser is integrated.
- **Coord scaling:** the live runner correctly translated bbox from 0–1000 normalized to pixel coords before sending to SAM2. SAM2's mask landed where the wall actually is.
- **Modal cold-start tolerance:** the SD Inpaint container loaded the 1.7 GB weights to the volume on first call (~60s including model load). No timeout. Subsequent calls will be much faster since weights are now committed to the Modal volume.

## What's weak

- **Travertine doesn't look like travertine.** SD Inpaint 1.5 has no material conditioning — the prompt `"photorealistic travertine wall surface, architectural interior, natural light, sharp texture detail, professional photography"` produces a vaguely cream-smooth wall, not the distinctive cross-cut limestone texture of actual travertine. This is the known reason the master plan ([docs/plans/master-plan.md](../../docs/plans/master-plan.md)) calls for **FLUX Fill + IP-Adapter** in v1: IP-Adapter takes the swatch image (`travertine.jpeg`) as image conditioning, which is the only way to reliably transfer a specific material's appearance.
- **Wall_1 bbox starts at y=0.** The wall_1 bbox is `(655, 0, 204, 574)` in normalized space — it includes the top of the image, which is sky/background. SAM2 correctly identified only the wall pixels within the bbox (the sky was excluded from the mask), so this didn't damage the output, but a tighter bbox from `tag_regions` would feed SAM2 a more constrained prompt.
- **SD Inpaint downsamples to 512×512.** The base render is 1259×848; the inpaint runs at 512×512 and the tile is upscaled back. This is a quality ceiling regardless of material — the v1 stack should run at native render resolution or do a tiled-inpaint.
