## Surprises / notes for the human

- **respx vs requests:** the task row says `Mock HTTP with respx (preferred) or responses`. `respx` is installed in the venv (0.23.1) but only patches `httpx`, not `requests`. All renderer modules import `requests` lazily inside `render()`. `responses` is not installed. To stay within the no-pip-install rule, I mocked `requests` directly using `unittest.mock.patch.dict(sys.modules, {"requests": MagicMock()})`. The coverage shape (assert on URL/body, return fake responses, simulate HTTP errors) is identical to what `respx` would give for an `httpx`-based client. If you want literal `respx` usage in the future, the renderers need to switch from `requests` to `httpx`. I did NOT make that change — out of scope for T11.
- **Polling:** all polling-based renderers (FLUX, Magnific, Replicate) use `time.sleep(...)` between polls. Each test monkeypatches the module-level `time.sleep` to a no-op so the test suite runs in 0.24s.
- **Recraft b64 path:** Recraft supports both `url` and `b64_json` response shapes; a separate test exercises the b64 path and asserts no follow-up GET is made.
- **Nano Banana:** isn't HTTP — it calls Modal. The test injects a fake `modal` module into `sys.modules` with a `Function.lookup` mock to verify the right app name (`arch-rendering-spike`) and function name (`render_from_model_view`) are looked up, and that the screenshot bytes flow through unchanged.

## Follow-ups

- Consider migrating the renderers from `requests` to `httpx` if you want to use `respx` consistently — it offers more expressive matchers (URL regex, JSON body assertions) than `unittest.mock` and is the de-facto modern HTTP-mock library. Not urgent.
- The tests don't cover timeout paths (`_POLL_TIMEOUT_S` exceeded). Those branches are simple and would slow the suite if exercised with real sleeps; mocking `time.monotonic` would work if you want them covered later.
