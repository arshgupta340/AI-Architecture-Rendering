## What was done
Created `spike/schemas.py` with three Pydantic v2 models. `BBox` enforces `x, y >= 0` and `w, h > 0`. `Region` carries the bbox, a string `label`, a `confidence` in `[0, 1]`, and an optional `parent_id` (for sub-regions like mullions inside windows). A field validator constrains `label` against the `Region.LABELS` ClassVar tuple (the 13 categories from the task spec: wall, floor, ceiling, window, door, mullion, roof, ground, sky, vegetation, furniture, person, vehicle). `TagRegionsResponse` wraps `list[Region]`. The module has no runtime side effects and no network/import-time work beyond pulling pydantic.

## Surprises / notes for the human
- The label vocabulary is enforced via `field_validator` on a plain `str` field rather than a `Literal[...]` type alias. This was a deliberate trade-off: it keeps the allowed list discoverable as `Region.LABELS` (a real attribute the VLM prompt builder in T14 can iterate) without duplicating the strings. The Gemini structured-output config in T14 can pass `enum=list(Region.LABELS)` to the schema.
- `parent_id` is a free-form string (matches whatever the VLM assigns to other regions' `id`). No referential-integrity check at parse time — T16/T19 should validate the graph if needed.
- Pydantic v2 `ClassVar` semantics: tuple-typed ClassVars are treated as class attributes, not fields. Verified `Region.LABELS` is accessible on the class and not part of `model_dump()`.
