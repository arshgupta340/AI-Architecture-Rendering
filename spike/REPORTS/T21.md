## Code changes

### 1. Prompt revision — `spike/modal_app.py:tag_regions`

Rewrote the instruction string to fix five distinct issues from T17:

- **Explicit coord-space declaration.** Old prompt asked for "pixel coordinates of IMAGE 2." Gemini ignored this and returned 0–1000 normalized coords anyway. New prompt aligns with observed behavior: "use the standard Gemini 0–1000 normalized space relative to IMAGE 2. … The caller will rescale to actual pixels." No more ambiguity.
- **Tight-bbox-per-element rules.** Replaced the vague "prefer tight bounding boxes" with: "One bbox per ARCHITECTURAL ELEMENT, not per facade. A facade is NOT a wall — it is a collection of walls, windows, and mullions. Emit a separate 'wall' bbox for each contiguous opaque wall SURFACE between openings. A bbox that contains windows inside it is too loose for 'wall' — split it." Also explicit guidance for repeated elements (per-instance, not per-row, cap ~30).
- **Strict `parent_id` semantics.** Was being used as "spatial overlap" in T17. New: "parent_id encodes GEOMETRIC CONTAINMENT … Architecturally invalid containments are forbidden: a door is NEVER a child of a window."
- **Label discipline.** Explicit anti-mislabel guidance for the T17 errors: "door": real human-passage opening, NOT balcony glazing, NOT upper-floor windows; "mullion" only when visible (do not invent); roof vs wall (top horizontal/sloped vs vertical); focus on primary building.
- **Result motivation upfront.** "Downstream, each bbox is fed to SAM2 to produce a pixel mask … Bbox quality directly determines edit quality." Frames the task so the model treats tightness as the metric, not coverage.

### 2. Coord scaling — `spike/test_vlm_tagging.py`

Added `_scale_bbox_to_pixels(bbox_x, bbox_y, bbox_w, bbox_h, img_w, img_h) -> (px, py, pw, ph)` helper that rescales 0–1000 normalized coords to actual pixel dims of the render. `_draw_regions` now reads the render image size first and applies scaling per region before drawing. Saved JSON also now keyed by input stem (`tagged_<basename>.json`) instead of a fixed `smoke_test.json`, so successive runs don't overwrite.

### 3. Coord scaling — `spike/end_to_end_edit.py`

Added `_render_pixel_size(render_bytes)` + `_bbox_norm_to_pixels(region, img_w, img_h)` (intentionally kept symmetric with the visualization helper). `_run_segment_bbox` now rescales before constructing the SAM2 prompt and uses pixel coords in the cache key. Live runner prints both normalized and pixel bbox values for readability.

### 4. Test fixture update — `spike/tests/test_end_to_end.py`

Existing fixture used small bbox numbers (`x=20, y=5, w=15, h=20`) as if they were pixel coords. With the new normalized→pixel scaling logic they would scale to sub-pixel ranges on a 32×32 mock render. Bumped the test render size to `_RENDER_SIZE = (1000, 1000)` so normalized coords map 1:1 to pixels and the existing fixture values + assertions remain meaningful. All 34 tests pass.

## Improvements vs T17

All five Issue-A through Issue-E findings from T17 saw movement:

- **Issue A (coord-space bug):** FIXED. Scaling helpers in both the visualization driver and the SAM2 caller. Verified all 5 outputs respect the 0–1000 normalization (max_xy ≤ 1000 in every case).
- **Issue B (flat confidence):** UNCHANGED. Confidence values now range 0.85–0.99 instead of flat 0.95 across the board, but variation is too narrow to be a useful filter. Likely a Gemini 3 Pro limitation, not a prompt issue.
- **Issue C (loose wall bboxes):** FIXED. Pair 1 went from 1–3 facade-spanning wall regions in T17 to 11 wall strips between window rows; pair 5 (complex windows) split walls into 28 distinct strips.
- **Issue D (doors mislabeled as balcony glazing):** APPEARS FIXED. None of the 5 outputs reproduced the T17 pattern of placing "door" labels on upper-floor balcony glazing. The 2 doors in pair 1 are at the storefront level where doors actually exist.
- **Issue E (door inside window via parent_id):** FIXED. No invalid parent_id chains observed in any of the 5 outputs.

New gains:
- **Mullion detection.** First successful mullion hit (4 regions on the traditional/interior dining pair). T17 returned zero mullions.
- **77 tight per-window bboxes** on pair 1, vs T17's facade-level boxes. Direct evidence that the "per-element not per-facade" guidance worked.

## Key finding (the load-bearing insight from T21)

**The Spike 3 gate passes on photoreal renders but fails on raw 3D-model screenshots.**

Pair 1 (photoreal render input) → 94 tight regions, all major architectural categories hit, clear PASS.

Pair 4 (raw screenshot input) → 25 regions, **zero windows** despite the screenshot showing many bright-blue window blocks on tower and podium facades. The model identified building masses and roofs but couldn't interpret the color-block windows as windows without photoreal context. Pair 5 (complex windows screenshot) returned 69 windows but zero mullions, even though the entire facade is essentially a mullion grid.

This empirically confirms the design assumption baked into the pipeline: `tag_regions` should always run on the photoreal render, not on raw screenshots. Pair 1 is the only one of the 5 that tests the production scenario, and it clears the gate.

## Spike 3 gate verdict

Strictly against the plan's wording ("≥80% of major elements correctly tagged on 5 diverse screenshots") — **does not clear**, primarily because pairs 2–5 weren't tested in production shape (screenshot+render pair) within budget.

Pragmatically — **clears on the production-shape pair (pair 1) with a dramatic quality improvement over T17**. The remaining work to fully close the gate is a budget question (run Nano Banana on the 4 new screenshots, then re-tag), not a quality question.

## Remaining issues

- **Mullion detection inconsistent.** Hit on traditional interior, missed on the complex-windows facade where mullions are the dominant feature. Likely needs a prompt addition that calls out tightly-spaced grids specifically.
- **Confidence still effectively flat.** 0.85–0.99 range. Cannot be used as a filter.
- **Over-segmentation in some categories.** Pair 1 has 4 "roof" regions where only ~2 roof planes are visible. Not wrong, but noisy.
- **No reliable mechanism for non-architectural exclusion.** Pair 4 has `ground` / `sky` absent entirely.
