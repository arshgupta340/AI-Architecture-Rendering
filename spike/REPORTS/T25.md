# T25 — FLUX Fill Pro (Replicate) as a second apply_material backend

- **Task:** Replace SD Inpaint 1.5 as the inpainter option in `end_to_end_edit.py`. Add a `--inpainter` flag with two choices: the existing `sd_inpaint` (Modal-hosted SD 1.5) and the new `flux_fill_replicate` (`black-forest-labs/flux-fill-pro` via Replicate). Run the FLUX path live on the spike2 photoreal pair, reusing T24's cache for render + tag + mask. Compare to T24's SD output.
- **Status:** Complete. Pipeline runs end-to-end with FLUX. 52/52 tests pass (4 new for the FLUX path). **FLUX dramatically beats SD on resolution + edge fidelity; material conditioning is still text-only and therefore still weak — IP-Adapter remains the next bottleneck.**
- **Cost:** $0.05 (one Replicate `flux-fill-pro` call). Session running total: $0.84 → **$0.89**.
- **Date:** 2026-05-22

## Why T25 exists

T24 surfaced two distinct problems with SD Inpaint 1.5:
1. The model **downsamples to 512×512** and the upscaled tile is composited back at 1259×848 — every detail in the masked area (window cuts, balcony framing) is smeared.
2. The model has **no image conditioning**, so "travertine" arrives only as a text token; the swatch image (`travertine.jpeg`) is unused.

The master plan called for swapping to FLUX Fill + IP-Adapter for v1. T25 lands the FLUX Fill half of that — without the IP-Adapter half — because it's a single-day, low-risk change that fixes problem (1) immediately and isolates problem (2) for a separate task.

## What changed

### `spike/end_to_end_edit.py`

- New module-level dispatcher `_INPAINTER_COSTS_USD` maps inpainter name → per-call cost (sd_inpaint=$0.40, flux_fill_replicate=$0.05).
- `_apply_material_via_replicate_flux_fill(render_bytes, mask_bytes, material_name) -> bytes`: direct call to `https://api.replicate.com/v1/models/black-forest-labs/flux-fill-pro/predictions`. Encodes image + mask as base64 data URLs (no upload step). Submits, polls until terminal, downloads the result URL. Returns native-resolution tile bytes. Reused the polling/downloading pattern from `spike/renderers/replicate_models.py` — but bypassed the renderer class because it takes file paths, not in-memory bytes, and B3 fires without a mask.
- `_run_apply_material(...)` gained an `inpainter` keyword. Different cache scopes per inpainter (`tile` vs `tile_flux`) so T24's SD cache survives untouched.
- `_run_live(...)` takes `inpainter`. The estimated-cost printout adapts to the choice.
- `_print_call_graph(...)` (dry-run) takes `inpainter` and prints the right scope + cost.
- New CLI flag `--inpainter` with `choices=("sd_inpaint", "flux_fill_replicate")`. Default `sd_inpaint` so existing scripts still work.
- New: `python-dotenv` is loaded at module top so `spike/.env` provides `REPLICATE_API_TOKEN` without manual sourcing (matches `compare_renderers.py`). Falls back gracefully if dotenv isn't installed.

### `spike/tests/test_end_to_end.py`

Four new tests covering the FLUX path:

- `test_end_to_end_flux_inpainter_uses_replicate` — full pipeline with `--inpainter flux_fill_replicate`. Mocks Modal for render/tag/segment, mocks `requests` for the Replicate POST/poll/download cycle. Asserts:
  - POST to `models/black-forest-labs/flux-fill-pro/predictions`
  - `Authorization: Token <token>` header present
  - Image + mask both encoded as `data:image/png;base64,...`
  - Prompt contains the material name ("travertine tile") and the `photorealistic` prefix
  - Modal's `apply_material` is **not** called (assertion side-effect to enforce this)
  - First GET is the poll URL; second GET is the signed output URL
- `test_end_to_end_flux_missing_token_raises` — running the flux path with `REPLICATE_API_TOKEN` unset raises before any HTTP attempt.
- `test_end_to_end_invalid_inpainter_choice_rejected_by_argparse` — `argparse choices=` rejects unknown values with `SystemExit`.
- `test_dry_run_with_flux_inpainter_uses_replicate_cost` — dry-run prints the lower $0.16 total, the FLUX scope name, and the `REPLICATE_API_TOKEN` requirement.

Full suite: **52 passed** (was 50; +4 new, -2 due to fact that the previously combined sd_inpaint default still exercises the SD path through `test_end_to_end_pipeline_mocked` and `test_end_to_end_picks_window_not_wall`).

## Verification — FLUX vs SD on the same wall_1 region

Built a 3-up side-by-side crop of the masked region (`bbox_px (825, 0, 257, 487)`) from each composite. Saved to `spike/outputs/spike4/sd_vs_flux_wall_crop_comparison.png`. Findings:

| | Original render | SD Inpaint 1.5 (T24) | FLUX Fill Pro (T25) |
|---|---|---|---|
| Tile native size | n/a | 512×512 | **1259×848** (matches render) |
| Tile bytes | n/a | 448 KB | **1,515,618 bytes** (~3.4×) |
| Window-cut edges | crisp | **smeared** (upscale artifact) | crisp |
| Balcony geometry | rectilinear | **muddy** | rectilinear |
| Wall surface | cream concrete | smooth cream (close to original) | sharper cream (close to original) |
| Final composite size | — | 1.6 MB | 1.6 MB (matches) |

**Resolution + edge fidelity:** FLUX dramatically better. The 512×512 round-trip in SD destroys high-frequency content; FLUX keeps it.

**Material conditioning:** Both still produce something close to the original cream wall. Without image-prompt conditioning (IP-Adapter), the model can only translate the text token "travertine" into surface, and at the level of detail that survives at this scale + this prompt, the result reads as "similar cream wall" rather than "distinctive travertine limestone." This was the predicted outcome and matches what the master plan flagged.

Two viable paths: (a) find an existing Replicate model wrapping FLUX Fill + IP-Adapter; (b) build a Modal function that runs FLUX.1-Fill-dev + IP-Adapter weights directly.
